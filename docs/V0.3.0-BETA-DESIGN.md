# v0.3.0-beta — Design Spec (Working Draft)

> **Status:** Working draft from a 2026-09-29 design conversation. Source-of-truth for v0.3.0-beta until the canonical SPEC.md is updated. Decisions marked [Settled] are user-confirmed; [Open] needs user input; [Deferred] is intentionally out of scope.

## TL;DR — the v0.3.0-beta MVP

The user-confirmed MVP for v0.3.0-beta:

1. **Daily view** with two modal flows: **Morning Grounds** (auto-triage, default) and **Mindful Selection** (per-item triage, override)
2. **Layouts** (2 types: Daily, Weekend) with date ranges, most-specific wins, soft delete
3. **Numeric trackers with goal** (e.g., "Cups of Water, goal 8"). Polymorphism planned but not built.
4. **Pre-populated sample layout** for new users; user picks from samples
5. **Components hide empty states** with prompts ("Add your first ..."), not silent hiding

**Deferred to v0.4.0-GA or later:**

- Text / icon tracker types (polymorphism)
- Wiki-style journal links with create-on-click popup
- Sub-task UI on task form (right-side table, parent dropdown)
- Settings page beyond Config tab
- Week / month / year views
- Past layouts gallery
- Visual completion rewards (butterflies / fireworks)
- Icon catalog details

## 1. Daily view — the modal flow

The daily page is the user's home view. The morning ritual is a **modal**, not a separate page.

### 1.1 Two modal variants

| Variant               | Default for who                                | Triage style                                                                        |
| --------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------- |
| **Morning Grounds**   | Most users (and new users until they override) | Auto-prepend rolled items to letter bucket; single "approve order" click to confirm |
| **Mindful Selection** | Users who set it as default in settings        | Per-item buttons (Move to A / Do Tomorrow / Let it go / etc.)                       |

**Naming confirmed by user:**

- Morning Grounds description: _"Grounding the day in what's possible"_ (cup of coffee icon)
- Mindful Selection description: _"Deliberately selecting what needs to be done today and weighing today's possibilities"_

### 1.2 Modal trigger conditions

The modal opens on site load when **any** of these are true:

- There are carry-overs from the day before (rolled items)
- There are items due today that aren't on today's task list
- There are items due tomorrow that aren't on today's task list

If none of these are true, no modal — user goes straight to the day's view.

**Which modal opens:** determined by the user's `settings.default_daily_modal` (DB-stored). Default = Morning Grounds.

### 1.3 Modal lifecycle

- Modal opens on site load when trigger conditions hit
- User triages (auto-acknowledge in Morning Grounds, or per-item actions in Mindful Selection)
- User clicks an action that closes the modal
- Modal closes; user is dropped into the **day's view** (the actual daily page)

### 1.4 Re-triage mid-day

A button on the day's view re-opens the modal (lets the user re-triage when priorities shift during the day). Not yet specified whether this is the same modal type or a different one.

## 2. Layouts — Daily & Weekend (2-type system)

The user simplified the original 3-type system (Daily/Weekday/Weekend) down to 2.

### 2.1 Two layout types

| Type        | Applies to                      |
| ----------- | ------------------------------- |
| **Daily**   | Every day within its date range |
| **Weekend** | Sat & Sun within its date range |

### 2.2 Specificity rule

**Most-specific wins**, combining type + range:

- Type hierarchy: Weekend > Daily (on Sat/Sun within Weekend's range)
- Range hierarchy: shorter date range > longer (1-day override beats year-long)
- Combined: a 1-day Weekend beats a year-long Daily; a year-long Weekend beats a year-long Daily on Sat/Sun

### 2.3 Lifecycle rules

- **Date ranges:** inclusive on both ends. Schema enforces no overlap.
- **Auto-update on save:** when a user saves a new layout, the system auto-sets `end_date` on the overlapping layout (yesterday's date for the new layout's start).
- **Soft delete:** setting `end_date` to a past date. No hard delete ever.
- **Adoption draft state:** when a user _adopts_ a layout (from default or future gallery), changes on the adoption day overwrite the same `layout_id`. The layout "locks in" at the user's local midnight. (Does NOT apply to user-created-from-scratch layouts; same draft rule applies — user confirmed.)

### 2.4 Schema shape (target)

```
layouts
  id              uuid
  user_id         uuid (FK users)
  name            text          -- e.g. "Summer 2026", "Birthday"
  start_date      date
  end_date        date          -- nullable; inclusive
  type            enum          -- 'Daily' | 'Weekend'
  adopted_from_template_id  uuid -- nullable; references templates if adopted
  created_at      timestamptz
  updated_at      timestamptz

layout_components
  id              uuid
  layout_id       uuid (FK layouts, cascade)
  component_type  enum          -- 'task_list' | 'schedule' | 'journal' | 'tracker' | ...
  instance_id     uuid          -- nullable; references the specific tracker / journal instance
  position        jsonb         -- x, y, w, h (grid coordinates)
  config          jsonb         -- per-component-type overrides
  created_at      timestamptz
```

`users` table needs `timezone` (IANA TZ name) added — used for lock-in and "today" semantics.

## 3. Components & the daily page

### 3.1 Component library (v0.3.0-beta MVP)

The component palette for v0.3.0-beta:

| Component             | Description                                            |
| --------------------- | ------------------------------------------------------ |
| **Task list**         | Today's prioritized tasks (A1, A2, B1, ...)            |
| **Schedule**          | Today's time blocks (the meetings "blocked out")       |
| **Journal**           | Today's journal entry (rich text, wiki-links deferred) |
| **Tracker (numeric)** | A counter with a goal (Cups of Water, goal 8)          |

Open question — does anything else ship in v0.3.0-beta (Pomodoro, Weather, Mood, Meals)? User said "keep it simple for now."

### 3.2 Empty-state behavior

When a component has no content, it shows an "Add your first ..." prompt, **not** silent hiding. Example: empty Water Tracker shows "Add your first cup."

If the user doesn't want a component, they **delete it from the layout** (remove from this layout only — the underlying tracker definition persists).

### 3.3 Drag-and-drop arrangement

- User can drag components to positions on the daily page
- Position stored in `layout_components.position` JSONB
- Reflow is NOT desired — user's positions are stable
- Empty components don't reflow (they show empty state)

### 3.4 Pre-populated sample for new users

- On signup, the system shows samples
- User picks one
- That becomes the first `layouts` row (with `adopted_from_template_id` set)
- Templates live in a separate `layout_templates` table (not built yet)

## 4. Task prioritization

### 4.1 Two systems coexist

| System                                               | Applies to                  | Lives on                       |
| ---------------------------------------------------- | --------------------------- | ------------------------------ |
| **Eisenhower Quadrant** (Q1/Q2/Q3/Q4)                | The full task list (master) | `tasks.quadrant`               |
| **ABC-123 daily priority** (A1, A2, B1, B2, C1, ...) | Today's task list           | `daily_priorities` table (NEW) |

**Why both:** Quadrant = the task's stable nature ("server crash" is always Q1). ABC-123 = the day's reality ("this Q2 task is A today, B tomorrow, C next week"). They're orthogonal dimensions.

### 4.3 Auto-roll behavior

- **What rolls:** incomplete tasks from yesterday
- **Where:** prepended to today's letter bucket (top of A, then A2, A3, ...)
- **Q4 special treatment:** Q4 (Delete) items get "consider deleting" treatment instead of "approve order"; action set = `[Delete, Move, Change quadrant, Keep anyway]`
- **Q1/Q2/Q3:** standard "highlight + approve order" gesture

### 4.4 Roll-over rule for daily priority position

Yesterday's A1 didn't get done → today's A1 (prepended, position carried forward implicitly via drag).

## 5. Tasks — schema changes needed

### 5.1 Rename quadrant enum to words

User wants the values to be words, not Roman numerals. Schema change:

```ts
// Current:
export const quadrantEnum = pgEnum("quadrant", ["I", "II", "III", "IV"]);

// Target:
export const quadrantEnum = pgEnum("quadrant", [
  "DO_FIRST", // Q1: Urgent and Important
  "SCHEDULE", // Q2: Important, Not Urgent
  "DELEGATE", // Q3: Urgent, Not Important
  "DELETE", // Q4: Not Urgent, Not Important
]);
```

User said "I don't like the roman numerals. Lets use the words not the roman numerals." Confirmation deferred to next session — but the strong implication is to rename.

### 5.2 Daily priorities — new table

```ts
export const dailyPriorities = pgTable('daily_priorities', {
  id: uuid().primaryKey().defaultRandom(),
  userId: uuid().notNull().references(() => users.id, { onDelete: 'cascade' }),
  taskId: uuid().notNull().references(() => tasks.id, { onDelete: 'cascade' }),
  date: timestamp({ withTimezone: true }).notNull(),  -- user's local date
  letter: pgEnum('daily_letter', ['A', 'B', 'C'])('letter').notNull(),
  // Position: stored in next-best-iteration of the drag-and-drop column type
  // (integer / fractional / linked list / updatedAt) — TBD
  createdAt: timestamp({ withTimezone: true }).notNull().defaultNow(),
  updatedAt: timestamp({ withTimezone: true }).notNull().defaultNow().$onUpdate(() => new Date()),
});
```

## 6. Trackers (numeric only for v0.3.0-beta)

### 6.1 Tracker schema

```ts
export const trackers = pgTable('trackers', {
  id: uuid().primaryKey().defaultRandom(),
  userId: uuid().notNull().references(() => users.id, { onDelete: 'cascade' }),
  name: text().notNull(),                         -- e.g., 'Water', 'Exercise'
  type: pgEnum('tracker_type', ['NUMERIC', 'TEXT', 'ICON'])('type').notNull(),
  goal: integer(),                                -- numeric goal (e.g., 8 cups)
  iconId: text(),                                 -- optional; references system_icons
  createdAt: timestamp({ withTimezone: true }).notNull().defaultNow(),
  updatedAt: timestamp({ withTimezone: true }).notNull().defaultNow().$onUpdate(() => new Date()),
});

export const trackerEntries = pgTable('tracker_entries', {
  id: uuid().primaryKey().defaultRandom(),
  trackerId: uuid().notNull().references(() => trackers.id, { onDelete: 'cascade' }),
  userId: uuid().notNull().references(() => users.id, { onDelete: 'cascade' }),
  date: timestamp({ withTimezone: true }).notNull(),
  value: text().notNull(),                        -- character field; UI parses by type
  createdAt: timestamp({ withTimezone: true }).notNull().defaultNow(),
});
```

**Polymorphism pattern:** value stored as `text`. The `type` column on `trackers` tells the UI how to parse / display.

### 6.2 Display rules (UI)

| Tracker type           | Display                                  |
| ---------------------- | ---------------------------------------- |
| NUMERIC (whole number) | N icons (e.g., 8 cup icons for "8 cups") |
| NUMERIC (real number)  | Bar fill (e.g., 50% filled)              |
| TEXT                   | The text content                         |
| ICON                   | The identified icon (e.g., smiley)       |

For v0.3.0-beta: **only NUMERIC is built**. TEXT and ICON are scaffolded in the schema but the UI doesn't expose them.

### 6.3 Icons (deferred details)

- **Catalog:** system-defined; ships later. User said "we'll determine the set of icons for the various tracker types later."
- **Numeric trackers MAY have an icon** (e.g., Water → cup icons, Exercise → pushup icons). User-confirmed.
- **Theme-dependent:** a few icons might depend on theme (light/dark/seasonal). Deferred.

## 9. Decisions that came up and were DROPPED

These were considered but explicitly rejected by the user during the conversation. Don't re-litigate them without strong reason:

- **3-type layout system (Daily/Weekday/Weekend)** — dropped. User simplified to 2 types (Daily/Weekend) because the Weekday concept was more complex than needed.
- **Auto-conversion Daily → Weekday on Weekend creation** — gone with the simplification.
- **Hard delete of layouts** — explicitly forbidden. Soft delete only via `end_date`.
- **Bulk approve-order with per-item buttons as default** — the wireframe showed per-item buttons; user clarified these are for Mindful Selection only, not Morning Grounds.
- **Inbox-zero daily triage on Morning Grounds** — explicitly rejected. Morning Grounds is a single "approve order" click, not per-item decisions.
- **"Advanced View" naming** — replaced with "Mindful Selection."
- **Q1 always defaults to A on the daily page** — user wasn't sure; resolved by user's "I'll select a layout" choice (per-layout user controls).
- **Widget grid where empty components reflow** — user picked empty-state prompts over reflow.

## 10. The conversation thread

The full design conversation happened over ~30 turns on 2026-09-29 / 2026-09-30 in the user's daily session. The thread went:

1. Initial feature requests: daily calendar, prioritized tasks with urgency/priority, journal with wiki links, rich text
2. Narrowing: bullet journal inspiration, today view, month view
3. "Grill me 1 at a time" — adversarial review of each decision
4. Today view specifics: Morning Grounds + Mindful Selection
5. Layout versioning: 3 types → 2 types simplification
6. Tracker system: numeric + text + icon polymorphism, value-as-text
7. Scope check at the end — user confirmed MVP for v0.3.0-beta

The conversation focused heavily on **product design decisions**, not engineering. Engineering questions (column types, framework choices, etc.) were deferred unless they were blockers.
